# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this package is

`drupal-visual-debugger` is a framework-agnostic JS/CSS engine that renders
on-screen overlays and a fly-out inspector panel from Drupal's Twig
theme-debug HTML comments. It has **no runtime dependency on Drupal** — it
only parses the `THEME DEBUG` / `THEME HOOK` / `BEGIN OUTPUT` comments that
Drupal's Twig debugging writes into the page.

This is a rewrite/extraction of the Javascript functionality inside the
`visual_debugger` Drupal module, which will be updated to carry a static,
compiled copy of the current library. It's also consumed by a separate
Drupal Visual Debugger Chrome extension as a bundled dependency. Because of
this dual consumption, **storage and translated strings are always injected**,
never accessed directly (see Architecture below) — code here must stay usable
outside of a Drupal page and outside of a browser extension's privileged
context.

For the page being inspected to produce any output at all, Twig debugging
must be enabled (`services.yml` → `twig.config.debug: true`, or the
`development.services.yml` override). Without it there are no debug comments
to parse.

## Commands

```
npm install       # install esbuild + sass (only devDependencies)
npm run build     # one-shot build: JS bundles + compiled CSS + fonts
npm run watch     # rebuild on change (uses node:fs watch, not esbuild's own
                   # watcher — see comment in build.mjs on why)
```

There is no test suite and no lint script configured in this package.

Build output (`dist/`) is gitignored and regenerated by `build.mjs`, which
produces four JS bundles (`esm`, `cjs`, `global`, `global.min`) from a single
`src/index.js` entry point via esbuild, plus compiled/minified CSS from
`sass/visual-debugger.scss` via Dart Sass (`visual-debugger.css`/`.min.css`),
plus the vendored icon font: its binaries copied to `dist/fonts/` and its
own precompiled CSS copied (not compiled — see Architecture) to
`dist/visual-debugger.fonts.css`. Before any of that, `build.mjs` also
(re)generates `generated/panelStyles.css` (also gitignored, kept out of
`src/` since everything there is otherwise hand-authored) — compiled panel
CSS plus base64-font-embedded copies of the icon CSS and Open Sans,
imported directly by `controllerPanel.js` and bundled into the JS output
(see Architecture's Shadow DOM note for why). When changing anything under
`src/` or `sass/`, rerun the build (or `watch`) before checking behavior —
nothing auto-serves `dist/`.

## Architecture

The core split is **parsing vs. rendering vs. everything-injectable**:

- `src/parser/drupalThemeDebugParser.js` — the *only* Drupal-specific file.
  Walks comment nodes under a root element and turns each
  `THEME DEBUG ... BEGIN OUTPUT` block into a plain `ThemeElement` object
  (see `src/model/themeElement.js`). Regexes here are written as real regex
  literals (not built from strings) deliberately — a `new RegExp("...\\s*...")`
  string silently drops the `\s` escape, which was a live bug in the original
  module. Also handles both `BEGIN OUTPUT` (default template) and
  `💡 BEGIN CUSTOM TEMPLATE OUTPUT` (theme-overridden template) — missing
  the custom-template variant would silently drop every themed element on a
  real site.
- `src/render/overlayLayer.js` — fully Drupal-agnostic. Builds/positions the
  per-element overlay boxes (`baseLayer`), owns single-selection state
  (`setChecked`/`isChecked`/`toggleChecked`), and keeps overlays aligned via
  `ResizeObserver` + a `MutationObserver` on `document.body[style]` (for
  things like an admin toolbar shifting body padding).
- `src/render/controllerPanel.js` — builds the fly-out inspector panel: tabs
  navigation, Active Element / Selected Element / List views, resize handle,
  activation persistence. Also fully agnostic — no `localStorage` or
  `Drupal.t()` calls directly; both are injected (see below). Renders
  behind a Shadow DOM boundary (`panelHost`/`panelRoot`, see the Shadow DOM
  note below) — `panelRoot` is the internal, styled content root every
  other function in the file queries/mutates, unchanged in behavior from
  before the shadow root existed; `panelHost` is the bare element actually
  appended to the document, exposed externally as `controllerLayer`.
- `src/index.js` (`init()`) — wires the three together: parse → build overlay
  → build panel → `overlay.attachControllerHooks(panel)`. Idempotent per
  root element (`CLASS_NAMES.initialized` guard). Returns a `destroy()`
  that composes `overlay.destroy()` + `panel.destroy()` and clears that
  guard. Each module's `destroy()` only tears down what *it* registered
  outside its own removable root element — anything attached to `document`/
  `document.body` (both persistent observers, the panel's two slider
  listeners) has to be disconnected/removed explicitly, or it — and the
  whole closure it holds onto — leaks forever even after the visible DOM
  is gone.

**Injection points, by design** (so the same code runs in a plain browser
page, inside the Drupal module, or inside a Chrome extension content script):
- `storage` — an object with `get(key, fallback)` / `set(key, value)`.
  Default is `webStorageAdapter` (`src/storage/webStorageAdapter.js`, wraps
  `localStorage`, fails soft). `createMemoryStorageAdapter()` exists for
  contexts without persistent storage (e.g. tests). The extension supplies
  its own `chrome.storage`-backed adapter.
- `strings` — plain object merged over `defaultStrings`
  (`src/i18n/defaultStrings.js`); the Drupal module wrapper overrides these
  with `Drupal.t()` output.

**Overlay ↔ panel communication** goes through two explicit interfaces
rather than DOM event bubbling or synthetic clicks:
- `ControllerHooks` (overlay → panel): `setActiveThemeElement` /
  `resetActiveThemeElement` (hover) and `setDefaultThemeElement` /
  `resetDefaultThemeElement` (selection), attached via
  `overlay.attachControllerHooks(panel)`.
- The panel's List tab calls back into the overlay engine directly
  (`overlay.toggleThemeElementSelection`, `overlay.setThemeElementVisible`,
  `overlay.hoverThemeElement`/`unhoverThemeElement`) rather than dispatching
  synthetic `click()`s on the overlay layer — two-way synthetic-click
  forwarding between the overlay and a list row would bounce a click back
  and forth. Conversely, each `ThemeElement` carries a `listRow.setActivated`
  callback (set when the List tab builds itself) so the overlay's own
  `setChecked()` can keep the List row's switch in sync when selection
  happens from hovering/clicking the overlay itself.

**Shared vocabulary**: `src/constants.js` centralizes every class name,
element ID, and data-attribute used by both the JS and
`sass/visual-debugger.scss`, and is kept byte-for-byte identical to the
original `visual_debugger` module's markup so the module's existing
`css/source` styles keep working. When adding a new UI element, add its
name here rather than inlining a string in the render code or the Sass.

**CSS**: `sass/visual-debugger.scss` is entirely var-driven — every rule
reads a `--vd-*` custom property (prefix is `$prefix` in
`sass/base/_variables.scss`) rather than a literal value, so a consumer can
re-theme the whole panel by overriding CSS custom properties without
touching the Sass. `sass/base/_variables.scss` is the source of truth for
those defaults. This same compiled CSS ships twice: once in the standalone
`dist/visual-debugger.css`/`.min.css` (for the overlay, light DOM), and
once embedded into the JS bundles for the panel's shadow root (see below) —
a page-level `--vd-*` override reaches the former, not the latter.

**Shadow DOM**: the controller panel (only — not the overlay) renders
inside `panelHost.attachShadow({ mode: 'open' })`. `panelHost` carries no
`visual-debugger*` classes (nothing for page CSS to match), and the shadow
root's own `<style>` — `generated/panelStyles.css`, regenerated by
`build.mjs`'s `buildPanelStyles()` on every build — opens with `:host {
all: initial; }` before the compiled panel CSS, so no inherited property
(including a page's `--vd-*` override) crosses the boundary either.
Everything else about the panel's construction is unaffected: `panelRoot`
(the styled content, living inside the shadow root) is queried/positioned
exactly as it was before the shadow root existed, since `querySelector`
and `position: fixed` both work the same whether or not their subtree
happens to sit inside a shadow tree — only rules/inheritance from *outside*
are blocked.

**Icon font**: `fonts/visual-debugger-icons/` is a vendored IcoMoon export,
untouched as downloaded (see README "Icon font" for how to regenerate it).
Its own `style.scss` isn't part of the Dart Sass compile — it's legacy
`@import` + unnamespaced-variable style, not worth adapting to this
project's `@use`-based setup. `build.mjs` copies its precompiled `style.css`
straight to `dist/visual-debugger.fonts.css` for the overlay (consumers
load it alongside `visual-debugger.css`). The panel's shadow root needs its
own copy instead of relying on that file — a relative `url()` inside an
injected `<style>` resolves against the *host page's* URL, not this
library's — so `buildPanelStyles()` rewrites the same icon CSS's `src:` to
a single base64 `data:font/woff` URI and folds it into
`generated/panelStyles.css`. This package's own `sass/base/_icons.scss`
handles icon *sizing/color* only (real Sass, compiled normally, present in
both copies) — the glyph-to-class `content:` mapping and `@font-face` live
solely in the (two, differently-packaged) IcoMoon CSS copies.

**Open Sans**: same reasoning, different mechanism. `fonts/open-sans/` is
three vendored static TTFs (Open Sans Semi Condensed — Light/300,
Medium/500, Bold/700; see README "Open Sans" for why 500 and not a "true"
400). Only the panel needs this (the overlay has no text), so there's no
standalone-dist-file half of this one — `buildOpenSansFontFaceCss()` in
`build.mjs` converts each TTF to WOFF2 via the `wawoff2` devDependency
(pure JS/WASM, no native build step) and base64-embeds all three directly
into `generated/panelStyles.css`, alongside the icon font. Fonts are never
fetched from Google at build or run time.

## Adding a new ThemeElement-driven feature (e.g. a new panel tab)

Follow the List tab as the template (`generateListTab`/`generateListItem` in
`controllerPanel.js`, `listElement*`/`listItem*` entries in
`constants.js`, `.list`/`.list-item` rules in the scss): add class
name/ID constants first, build the DOM in a `generate*` function that reads
from the `themeElements` array already passed into `createControllerPanel`,
wire any interaction back through the `overlay` parameter (never through
synthetic DOM events), and extend `defaultStrings.js` for any new label.
